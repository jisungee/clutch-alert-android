# 알림 판정 정책과 검토 항목

판정 기준은 [클러치 알림 발송 가이드라인 v1.0](클러치%20알림%20발송%20가이드라인%20v1.0.docx)이다. `NotificationRuleEngine.evaluate`는 이벤트의 `before`, `after`, 선호 팀 ID와 이전 판정의 맥락을 받아 후보 하나 또는 `null`을 반환한다. 누적 상태와 중복 관리는 `NotificationSession`이 맡는다.

## 구현 기준

- `FIRST_PITCH`는 데이터 공급자가 확인한 경기 첫 투구다. 기존 모의 JSON의 `GAME_STARTED`는 재생을 위한 상태 전환이므로 첫 투구 알림의 근거로 사용하지 않는다.
- 3아웃을 기록한 플레이에서 공격 또는 수비 종료와 이어지는 전환을 합친다. 이어지는 공수교대가 같은 전환이면 생략한다. 3아웃 기록 없이 시작만 확인된 반이닝은 시작 후보를 생성한다.
- 4득점에 도달하는 플레이에 빅이닝 문구를 붙인다. 가이드라인의 적시타 예시처럼 선호 팀 일반 득점과 빅이닝이 겹치면 빅이닝 제목을 쓰고 득점 정보도 포함한다. 홈런, 동점, 역전, 끝내기 또는 실점이 겹치면 해당 결과를 유지하면서 빅이닝을 함께 표시한다. 누적은 순서대로 수집한 같은 경기의 공격 반이닝 이벤트를 사용한다.
- `PlayDetails.walkOff`와 종료된 홈팀 승리 상태가 함께 있어야 끝내기로 표시한다. 타점 표현에는 명시된 `runsBattedIn`을 사용한다. 판독과 부상은 공식 결과나 확인 단계가 기록된 이벤트를 사용한다.
- 판정 중복은 재생 세션 안에서 경기와 이벤트 ID로 막는다. 선호 팀이 바뀌면 이후 이벤트부터 새 관점을 적용한다. 이미 판정한 이벤트는 같은 세션에서 재평가하지 않는다. 새 세션은 동일 이벤트를 다시 판정할 수 있다. 후보 ID는 경기·이벤트·선호 팀·유형으로 결정되며 재생 간에도 동일하다. 이 ID는 실제 발송 이력을 뜻하지 않는다.

## 후속 검토

- 첫 투구와 첫 공격·수비 시작이 공급자에서 같은 플레이를 가리키거나 별도 ID로 전달될 때의 결합 기준. 현재 첫 투구는 경기 시작 후보 하나를 생성하고 별도로 확인된 반이닝 시작은 시작 규칙을 따른다.
- 공급자가 3아웃 상태를 생략하고 반이닝을 바로 전환하는 경우의 종료 신호, 경기 종료로 수비 전환이 없는 경우의 데이터 표기, 서로 다른 이벤트 ID가 같은 실제 플레이를 나타낼 때의 공통 플레이 ID.
- 중간 이닝에서 구독을 시작하거나 이전 득점이 누락된 경우에 필요한 이닝 누적 점수 기준값. 판독 결과로 점수가 수정되는 경우의 정정 이벤트와 알림 정책.
- 판독 시작·결과나 부상 확인 단계가 서로 다른 이벤트 ID로 반복 보고될 때의 묶음 기준과 빈도. 실제 시스템 알림에서 세션을 넘어 재발송할지, 어떤 기간 동안 발송 이력을 유지할지도 별도 결정한다.
- 선호 팀 설정 UI와 디버그 후보 목록은 화면 연동 단계에서 결정한다. 4단계 UI에는 선호 팀 선택이 없으므로 임의 팀으로 자동 판정하지 않는다.

## 재생 연결 지점

다음 단계에서 `GameViewModel`의 기존 `collectEvents` 단일 소비자에 `NotificationSession.onEvent`를 연결한다. 재생 세션을 열 때 얻은 토큰을 해당 세션의 이벤트 수집과 함께 유지하고, 초기화나 종료 시 폐기한다. 늦게 도착한 이벤트를 현재 토큰으로 다시 표시하지 않는다. 엔진은 이미 초기화 전 큐를 폐기하며, 알림 세션도 폐기된 토큰을 거부한다. 실제 발송 결과는 별도 계층에서 추적한다.
